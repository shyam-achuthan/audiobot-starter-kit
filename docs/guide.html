AudioBots

Low-latency voice agents for sales, support and lead qualification, built for the Indian market. One agent handles website visitors (WebRTC) and, from Phase 7, phone calls over SIP. Everything runs in Docker, mostly on open-source software.

  • LiveKit (self-hosted)
  • Sarvam STT & TTS
  • Gemini via LiteLLM
  • English · Hindi · Hinglish · Tamil · Telugu · Kannada · Malayalam
  • Docker Compose

What works today

Voice loop

Microphone to speech recognition to LLM to speech, streamed end to end, with barge-in (interrupt the bot by talking).

Auto language

Detects the caller's language on every utterance. The reply and the voice switch to match.

Local turn-taking

Voice activity detection and an end-of-turn model run inside the agent. Nothing goes to LiveKit Cloud.

Latency telemetry

Every turn's timings (end of turn, STT, LLM, TTS, total) are logged and shown live on the demo page.

Workflow agents

A receptionist hands off to lead-qualification, sales or support agents, keeping the conversation history.

Saved to Postgres

Every call, turn, lead, support ticket and callback request is stored through the NestJS API (Sequelize).

Knowledge base

Agents answer from your documents, FAQs and web pages, in any supported language, and quote prices only from them.

Visual setup

Business profile and knowledge are managed on admin pages, not in config files.

Status: Phases 0–3 are done: the stack, the voice loop, workflows with tools and storage, and the knowledge base with visual product setup. The full admin dashboard, CRM sync, recording and SIP come in later phases. See the roadmap.

Install

  1. Clone the repository 
    git clone git@github.com:shyam-achuthan/audiobot-starter-kit.git audiobots
cd audiobots
  2. Run the setup script It checks prerequisites and creates .env with generated secrets and your LAN IP. It then asks for your Sarvam and Gemini keys (input is hidden), builds and starts the containers, waits for them to become healthy, and tests the API and the LLM. 
    ./setup.sh

    Options: --yes runs without prompts, --no-start only prepares .env. It's safe to re-run; existing values and data are kept.

  3. Talk to the bot Open http://localhost:3000/demo in Chrome, pick a workflow, click Start call, allow the microphone, and say hello in any supported language.
First build is slow on some networks. The agent image downloads about 200 MB of Python packages from PyPI. If your ISP's route to PyPI is slow, this can take 20–40 minutes. The Dockerfile caches the heavy layer, so later builds take a few minutes. See Troubleshooting.

Manual setup (without the script)

make env                 # create .env (secrets + LAN IP)
$EDITOR .env             # set SARVAM_API_KEY and GEMINI_API_KEY

Vertex AI (Gemini from Mumbai)

The Gemini API in Google AI Studio is served from outside India, and from here its time to first token was 0.8–1.7 s. Vertex AI can serve Gemini from asia-south1 (Mumbai), which should cut a few hundred milliseconds. This is optional.

  1. Pick a Google Cloud project at console.cloud.google.com and note its project ID.
  2. Enable the Vertex AI API: APIs & Services → Library → "Vertex AI API" → Enable.
  3. Create a service account: IAM & Admin → Service Accounts → Create, name it audiobots-llm, role Vertex AI User.
  4. Create a JSON key: open the account → Keys → Add key → JSON. Save it as infra/litellm/secrets/vertex-sa.json. That folder is gitignored and mounted read-only into LiteLLM.
  5. Set the project in .env: VERTEXAI_PROJECT=<id>, VERTEXAI_LOCATION=asia-south1, then docker compose up -d --force-recreate litellm.

The same steps with the CLI (needs brew install --cask google-cloud-sdk and gcloud auth login):

P=your-project-id
gcloud services enable aiplatform.googleapis.com --project $P
gcloud iam service-accounts create audiobots-llm --project $P
gcloud projects add-iam-policy-binding $P \
  --member "serviceAccount:audiobots-llm@$P.iam.gserviceaccount.com" --role roles/aiplatform.user
gcloud iam service-accounts keys create infra/litellm/secrets/vertex-sa.json \
  --iam-account audiobots-llm@$P.iam.gserviceaccount.com
Not wired as the default yet. Once the key is in place, the next step is to benchmark which Gemini models Vertex serves in Mumbai and point agent-fast at the fastest one.

Architecture

LiveKit carries the audio. The Python agent runs the conversation. The NestJS API owns data and business logic. LiteLLM is the single gateway to every LLM and embedding provider, so providers change in config, not code.

Design principles

  • The agent only handles the conversation. Leads, tickets, callbacks (and later knowledge search and webhooks) live behind the NestJS API. The agent calls them as HTTP tools, authenticated with AGENT_API_TOKEN.
  • Every model is behind an alias. The agent asks LiteLLM for agent-fast, not for a vendor model, so a switch is a one-line change in infra/litellm/config.yaml.
  • Hosted first, self-hosted later. STT, TTS and LLM providers sit in a registry (agent/pipeline.py), so open models (IndicConformer, Indic Parler, vLLM) can drop in later.
  • Data stays local. Turn detection runs in the container, and session recording to LiveKit Cloud is turned off.

How a call works

  1. Token The demo page calls POST /v1/livekit/token (through the web app's /backend proxy) with the chosen workflow. The API creates a fresh room and a 15-minute token. The workflow goes into the participant metadata.
  2. Join The browser joins the room over WebRTC. LiveKit automatically dispatches an idle agent worker process to the new room.
  3. Greet The agent reads the workflow, creates a call record through the API, builds the pipeline from .env settings, and greets the caller as an AI assistant.
  4. Listen Silero VAD detects speech. Sarvam streams interim transcripts (shown as live captions) and detects the language.
  5. End of turn After 0.25 s of silence, the local turn detector (English and Hindi) or a fixed delay (other languages) decides that the caller has finished. The transcript is finalized.
  6. Reply The LLM streams its reply. Sentences go to Sarvam TTS as they are produced, so speech starts before the full answer exists.
  7. Act When needed, the LLM calls a tool: save lead details, create a ticket, book a callback, look up a ticket, or transfer to another agent. Tools call the API. An API error (for example an invalid phone number) goes back to the LLM as advice ("ask the caller to repeat it").
  8. End The agent says goodbye and ends the call, or the caller hangs up. The API then marks the call ended and stores its outcome, turn count and median latency.
  9. Interrupt If the caller talks over the bot, playback stops at once (VAD-based barge-in). If the "interruption" turns out to be just noise, the bot resumes.
  10. Telemetry Each finished turn publishes its text and timings on the room's agent data channel and saves them to call_turns. The demo page shows them live.

Setup & knowledge

Everything the agents know about your business is managed in the browser at localhost:3000/admin. No config files are involved.

  1. Business profile (/admin/setup) Name, what you offer, industry, website, support hours, callback hours and extra instructions (e.g. "Always mention the 14-day free trial"). Agents read this at the start of every call, so changes apply to the next call.
  2. Knowledge (/admin/knowledge) Create a knowledge base, choose its embedding model and which agents may use it, then add sources. Each source shows live status: pending → processing → ready (or error with the reason, and a Retry button).
  3. Test Use Test search on the knowledge page to see exactly what agents will find, then try a call on /demo and mark setup complete.
SourceHowNotes
FilesDrag and drop, or choose filesPDF, Word (.docx), .txt, .md, up to 15 MB each. Scanned PDFs need OCR first.
FAQQuestion + answer formBest for precise, short spoken answers. Each FAQ is one searchable unit.
WebsiteA page URL, or a sitemap.xml (up to 200 pages)Public sites only. Private, local and Docker-internal addresses are blocked. Pages that need JavaScript to show content can't be read.

How agents use it

  • Every agent has a search_knowledge tool. Sales and support call it for questions about products, plans, prices, policies, hours and troubleshooting. Support searches for the documented fix before suggesting anything.
  • Prices and policies are only quoted from search results. If the answer isn't in the knowledge base, the agent says a specialist will confirm and offers a callback. It never guesses.
  • Search works across languages: a Hindi or Tamil question finds English documents, and the agent answers in the caller's language. Only results scoring 0.45 or higher are used.
  • Text is split into ~800-character chunks on sentence boundaries (including ।) and embedded with embed-gemini (Gemini embeddings, 768 dimensions) through LiteLLM. Changing a knowledge base's embedding model re-indexes it automatically.
Try it with sample data. samples/knowledge/ has a fictional product, QuickBill: a price list (Markdown), policies (Word) and a troubleshooting guide (PDF). Upload all three on the knowledge page, set the business name to QuickBill, and ask the demo about the Business plan price or refunds.
Protect the admin area before exposing the server: set ADMIN_PASSWORD (and optionally ADMIN_USER) in .env to require a browser login for /admin. Full admin accounts arrive in Phase 4.

Demo page

localhost:3000/demo is a test console for the voice agent.

  • Workflow picker: Receptionist, Lead qualification, Sales or Support. The choice is sent with the token request.
  • Status line: connection, agent state (listening, thinking, speaking) and detected language.
  • Conversation: your transcribed words and the bot's replies. Interrupted replies are marked, and live captions appear while you speak.
  • Latency table: end of turn, STT, LLM first token, TTS first audio and voice-to-voice for every turn, plus the median. Values over 800 ms are highlighted.
Use a real browser. Microphones work on http://localhost in Chrome and Edge. Embedded or preview browsers often block the mic. For another device on your network you need HTTPS (planned with the production setup).

Workflows

Each workflow is its own agent with a role prompt (agent/prompts.py) and tools (agent/workflows.py). Agents share one call record and hand off to each other with the conversation history, so the caller never repeats themselves. None of them quote prices or policies yet; they offer a specialist callback instead. The knowledge base arrives in Phase 3.

AgentDoesTools
router (Receptionist)Finds out what the caller wants and transfers straight away, without asking permissiontransfer_to_sales, transfer_to_support, transfer_to_lead_qualification
lead_qualificationCollects name, need, team size, budget, decision maker, timeline and phone one question at a time, scores the lead 0–100, books a specialist callbacksave_lead_details, finish_qualification, transfer_to_sales
salesUnderstands needs, handles objections, books a specialist callback for pricing, a demo or a proposalrequest_callback, save_contact, transfer_to_lead_qualification, transfer_to_support
supportClarifies the problem, suggests simple fixes, raises a ticket with a priority, looks up existing tickets by number or phonecreate_support_ticket, lookup_tickets, transfer_to_sales
All agentsCallback from a person on request, then hang up after the goodbyerequest_human_callback, end_call

Guardrails built into the tools

  • Phone numbers must be confirmed. Tools that save a number require phone_confirmed=true. Without it they tell the LLM to read the number back in groups ("98450, 12345") and wait for a yes.
  • Indian numbers are normalized to +91…, including spoken formats ("098450-12345") and Indian-script digits (९८४५…, ௯௮…). An invalid number makes the agent ask again.
  • Placeholders are dropped. If the LLM fills an optional field with "not provided" or an invalid email, that field is skipped instead of failing the whole save.
  • Ticket numbers are spoken digit by digit ("ticket number 1 0 1 2"), and the reply language stays pinned to the caller's language across handoffs.
Callback-only booking. There's no calendar in v1. "Book a meeting" and "talk to a person" both become a high-priority callback ticket with the caller's preferred time, in their own words. Live transfer to a human comes with SIP in Phase 7.

Data & API

The NestJS API owns all data, through Sequelize (sequelize-typescript models). The schema comes from versioned migrations in api/src/database/migrations/, applied automatically when the API starts (disable with AUTO_MIGRATE=false). /health reports the latest applied migration.

TableHolds
callsOne row per call: room, channel, starting workflow, agent path (e.g. router → support), language, status, outcome, caller name and phone, turn count, median voice-to-voice latency
call_turnsEvery turn: agent, language, caller text, agent text, interrupted flag, and latency per stage (end of turn, STT, LLM, TTS, total)
leadsName, phone (+91…), email, company, need, team size, budget, authority, timeline, score, status (new / qualified / unqualified / callback), preferred callback time
ticketsSupport issues and callback requests: number (TKT-1001 upwards), type, subject, description, priority, status, contact, preferred callback time
business_profilesSingle row edited on the Setup page: name, description, industry, website, hours, extra instructions, setup completed
knowledge_basesName, embedding model, vector size, which agents may use it
kb_documentsSources (file, FAQ, URL) with extracted text, status, error and chunk count
kb_chunksText chunks with their pgvector embedding (HNSW-indexed for cosine search)

Call outcome only moves up in priority: callback_requested > ticket_created > lead_captured > info_only > abandoned.

Swapping providers

LLM: edit one file

Aliases live in infra/litellm/config.yaml. To point agent-fast at another model, change its model: line, for example vertex_ai/…, groq/…, or a self-hosted openai/… with an api_base. Then run docker compose restart litellm. Fallbacks are listed under router_settings.

Avoid "thinking" models for voice. Models that reason before answering add seconds of silence. Disable reasoning (reasoning_effort: disable) or use Flash-Lite-class models.

STT / TTS: add a registry entry

In agent/pipeline.py, add a factory to STT_PROVIDERS or TTS_PROVIDERS, then select it with STT_PROVIDER or TTS_PROVIDER. Install the matching livekit-plugins-* package through agent/requirements-plugins.txt. That layer is cached separately, so only the new package downloads.

Security & secrets

  • .env and infra/litellm/secrets/* are gitignored. Never commit keys. setup.sh sets .env to owner-only permissions.
  • Generated secrets are random per install. Rotate them by deleting a line from .env and re-running make env.
  • Browser tokens are short-lived (15 minutes) and scoped to a single new room.
  • Postgres, LiteLLM and RustFS listen on localhost only. LiveKit and the web app are reachable on your LAN.
  • Recording upload to LiveKit Cloud is disabled. Call recording (Phase 6) will play a consent prompt first and store audio in your own RustFS.
  • Production (later): TLS in front of LiveKit and the web app, admin authentication, and DPDP Act retention settings.

Demo says "Waiting for agent…" foreverCheck make logs s=agent. Usually the agent isn't healthy yet, or it crashed while starting the session.
"Agent error (config): … API key is required"Add the key to .env, then docker compose up -d --force-recreate agent litellm.
"Microphone unavailable: Permission denied"Allow the mic for localhost in Chrome site settings. Embedded preview browsers can't use the mic.
Connected but no audio, or the call drops after changing Wi-FiLiveKit is advertising your old LAN IP. Run make ip.
LLM test returns 408 / timeoutThe model is "thinking" (e.g. gemini-flash-latest). Use Flash-Lite or disable reasoning in infra/litellm/config.yaml.
LLM returns 429Gemini quota or rate limit. Check your AI Studio quota or use Vertex AI.
Port already in useAnother app holds one of the published ports. Stop it, or change the host-side port in docker-compose.yml.
.env not writableIt was edited with sudo. Run sudo chown $(whoami) .env.
Containers have no internet (npm or pip hang during build, agent can't reach Sarvam) while the Mac is fineCheck IPv4: curl -4 -m 8 https://www.google.com. Docker's container network uses IPv4 only. On some networks only IPv6 works (seen on a home router, and with VPN kill switches), and Sarvam has IPv4 addresses only. Fix the network (restart the router, turn off the VPN kill switch, or try another network). For a corporate proxy, set OUTBOUND_PROXY.
Agent goes quiet for 20 s or more, or the call drops; LiteLLM logs show 429 RESOURCE_EXHAUSTEDYour Gemini key hit its quota. The free tier allows only 20 requests per day per model, which a few test calls use up. Enable billing for the key in Google AI Studio (pay-as-you-go), or use Vertex AI. Until then LiteLLM falls back to Flash-Lite automatically: calls keep working, but turns that use tools are slower.
A source stays in error on the knowledge pageThe error text says why: e.g. "No readable text found" (scanned PDF without OCR), "too little readable text" (page needs JavaScript), or "Private, local or internal addresses are not allowed". Fix it and press Retry.
Agent says it will save or book something, then asks for the number againA tool refused the request; see make logs s=agent and search for ToolError. The message says why, e.g. "phone is not a valid number".
Bot replies in the wrong languageCheck the agent logs for language switch lines. If STT detects correctly but the reply drifts, try LLM_MODEL=agent-smart.
